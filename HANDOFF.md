## 16) Kill a character (mark deceased) + posthumous alerts (follow-up)

Nothing is deleted, so **Kill ⇄ Resurrect is a full toggle** and fantasy resurrections restore the original entity untouched. This deliberately does **not** touch `trashed_at` (that is Trash soft-delete, a separate concept).
- **Client** (`src/entityRelations.ts`): new `getDeath(raw)` → `{ chapter, at } | null`, alongside `getOwnerId`.
- New `src/chapters.ts`: `chapterNumber(c)` (`String(number || order+1)` — same blank-number fallback as the reader) and `chapterLabel(c)`. Shared by the modal and the Bible grid.

  - New `deathDraft` state + `kill(chapterId)` / `resurrect()` helpers (both `updateEntity({ fields })`, reload, `onChanged`).

  - `parseEntityFields` / `deathChapterFor(entity)` (resolves the death chapter row, or null).
  - `refreshPosthumous(entityId)`: deletes posthumous alerts at/before the death chapter, then **inserts one `posthumous` alert per chapter (after death) where the entity is still mentioned** — flashbacks or continuity slips. ## 23) Entity merge — the Aliases field absorbs a duplicate card

## 40) Duel — offline fights, snapshots and Markdown
- **What it is.** Planning → Duels: two sides of one to three Characters fight, scored by a deterministic offline engine that also writes template prose. No AI, network, new dependency, or live lookup after saving. The same feature adds a **Duels** subsection to the Markdown book.
- **Rules and formula.** Per fighter: `10 + powerRank×2 + min(abilitiesUsed, 3)×1.5 + attack + defence`, where attack/defence are the **highest** selected Item rank whose role allows it (not a sum). Per side: `raw = Σ fighters`, `numbers = (fighters − 1) × 2`, `score = (raw + numbers) × (1.5 if picked more skilled)`. `P(A) = clamp(scoreA / (scoreA + scoreB), 0.15, 0.85)`; the crypto seed's first `mulberry32` output is the stored roll. A chosen winner bypasses the roll and forces `skillSide: null`; otherwise A wins when `roll < P(A)`, else B. Up to 3 per side, no Character twice, and an Item may be shared within one side but never across sides. The same Character cannot be on both sides.
- **Item roles.** `fields.role` is `offense | defense | both | none`; absent/unknown means **Both**, which is deliberately the strongest. Labelling an Item Offense or Defense can therefore score it lower than leaving it unclassified. The Item editor's segmented control writes only a real choice, and the Markdown export shows role beside rank. Ranks are positional: Item rank `ITEM_RANKS.indexOf(rank) + 1` (Mundane 1 … Singular 6, unknown 0); power rank is the book ladder's `(sort_order, id)` position + 1. `ITEM_RANKS` is duplicated in `server/duel.mjs` and `EntityPanel.tsx`; changing one without the other silently changes scoring.
- **Data model and routes.** `duels` stores id, title, `sides` JSON, `outcome` JSON, narrative and `created_at`; `CREATE TABLE IF NOT EXISTS` means an existing book gains it on boot. The sides are a frozen snapshot — names, dead marks, power ranks, selected ability names in stored order, Items with the role/rank used, and terrain. There are no foreign keys, so deleting, trashing or merging a fighter leaves the saved card readable. `GET /api/duels` lists newest first; `POST /api/duels` validates the whole payload before inserting and auto-titles the fight; `DELETE /api/duels/:id` is hard deletion. There is no PATCH. `allDuels()` gives the list and export one ordering.
- **Builder flow.** `＋ New duel` opens two side columns; fighters come from a filtered picker or from **New character…**, which creates a real Character inline. Loadouts start empty, cap abilities at 3, read Items from `fields.owners`, and show rank/role; cross-side Items are blocked while same-side sharing is flagged. Terrain is Random from Locations (client-side, re-rollable) or Custom (80-character cap); blank means none. **Generate duel** asks first whether one side should win, and only if not, which side is more skilled. The submit is locked against double-clicks. Success shows the shared snapshot card with its account open and **New duel / Change setup / Back to Duels**. The saved list reuses the same card, newest first, with Delete. Leaving while any builder state is unsaved asks for confirmation; after a success, **Change setup** alone is quiet, but any subsequent builder edit re-arms the confirmation.

## 41) Automatic Chekhov's-gun scan
- **What it is.** Planning → Chekhov's Guns can now suggest objects the prose has planted. The scan is pure and offline: `server/gunscan.mjs` uses deterministic signals only, with no AI, network, new dependency, or live lookup after a candidate is added.
- **When it runs.** A chapter gets one automatic scan on its **first save with non-empty text**; later revisions do not rescan. `gun_scans` stores that one-shot marker. Existing chapters stay untouched until the writer uses **Scan chapters** in the Guns header, which replaces pending suggestions for the selected chapters and marks them as scanned.
- **What it looks for.** Known Items, Locations and Organisations are high-precision mentions. New candidates come from concrete object phrases, plus places, information, skills and traits only when the signals are strong. Signals include being handled/acquired, described, repeated, possessed, at a paragraph end, or surrounded by promise language. Similes, plural set-nouns, bare phrases, scenery parts and consumables are penalised so they do not crowd out the primary suggestions. Each chapter keeps at most **two primary** suggestions and up to four lower-tier ones behind **Show more**; a chapter with no primary gets no suggestion at all.
- **Where results go.** Candidates are stored in `gun_candidates` with chapter, title, normalized title, excerpt, score, signals, tier and status. They stay hidden until Planning → Guns shows **Found in your chapters**. **Add gun** creates a real gun immediately with the candidate title and its chapter as *planted in*; notes, payoff intent and planned payoff stay blank for the writer. **Not a gun** writes the normalized title to `gun_ignored`, rejects every matching pending row, and suppresses that suggestion in every chapter from then on. Accepting a candidate also keeps that normalized title out of later scans.
- **The reminder.** `GET /api/guns/review` returns `due` only when pending gun candidates exist and `gun_review_later_on` is not the server's local calendar day. Opening Planning shows the **Potential guns found** popup once per visit: **Look now** switches to the Guns tab, **Later** writes today's date and leaves the candidates in place. The popup returns on the next local day while anything is still pending. The first review response of the visit decides the prompt, so a manual **Scan chapters** later in the same visit does not pop it open after the fact.
- **UI and routes.** The Guns header now has the same **Scan chapters** modal as Questions. `ScanModal` takes a `questions | guns` kind; the selection, Select all and busy states are shared. New routes: `POST /api/guns/scan`, `GET /api/guns/candidates`, `POST /api/guns/candidates/:id/resolve`, `GET /api/guns/review`, `POST /api/guns/review/later`. The existing gun routes are unchanged.
- **Calibration and tests.** The signal thresholds were tuned against a read-only copy of the real five-chapter book under `/tmp/opencode/gun-calibration/`; the real book was never written to. Committed tests remain synthetic: `server/gunscan.test.mjs` covers handled/repeated objects, known Items, global ignore, existing guns, similes, the two-primary cap, abstract promises, and plural/singular ignore. Three route tests cover the automatic first pass, hidden storage, Add, Later, global rejection and manual rescan. Final: `npm test` **159/159**, `npx tsc --noEmit` **0**, `npx vite build` OK.
- **Real-book pass (22 Oct).** Against a throwaway copy `/tmp/opencode/gun-test/book.db`, `POST /api/guns/scan` on all five chapters found **14** candidates (**Toy**/**A new doll** in ch.1, **A mystery** in ch.3, **A spear**/**Weapons** in ch.5; ch.2 and ch.4 none). Add created a blank gun with its planted chapter; Not a gun kept the title out of a re-scan; re-scan replaced pending rows and left accepted/rejected rows alone. In Chromium, Show more revealed the lower tier, Add/Not a gun worked, the popup appeared only on the first load of a visit, **Later** quieted it until the next local day, and **Look now** landed on Guns. A new non-empty chapter auto-scanned once and a later edit did not rescan; a manual scan replaced that one pending row. Two defects found and fixed: a manual scan during a visit opened the popup after the fact, and rejecting **Weapons** let **A weapon** return on the next scan. The real book's mtime did not change.
- **Known limits.** This is a heuristic, not understanding: it can still pair a weak object with a real one (a toy and a doll in the same chapter), and a strong plural set can sit in **Show more** below a singular primary. It cannot confirm payoff because v1 detects plants only, and it does not rescan after later edits unless the writer asks. There is no un-ignore UI, and candidates do not appear in the Markdown export.

## 51) Story timeline — Map, explicit Story events, read-only markers
- **Scope.** A new **Timeline** view in the main rail, with **Map** first and **Story** second. The Map is manuscript structure; Story is an explicit chronology. Story order is manual and deliberately separate from chapter order, so a flashback can be placed where it belongs without moving the chapter.
- **Data model.** `server/db.mjs` adds `timeline_events` (`title`, `summary`, nullable `chapter_id`, free-text `story_time`, integer `story_order`, `kind`) and `timeline_event_entities` (`event_id`, `entity_id`, `role` = `participant | location | item`). Both are `CREATE TABLE IF NOT EXISTS`; indexes cover story order, chapter placement and entity links. A deleted chapter nulls `chapter_id` (`ON DELETE SET NULL`) and leaves the event; a deleted entity cascades only its link (`ON DELETE CASCADE`) and leaves the event. The chapter is an anchor, never the chronology.
- **Routes and validation.** `GET/POST /api/timeline/events`, `PUT /api/timeline/events/:id`, `DELETE /api/timeline/events/:id` and `PUT /api/timeline/events/reorder`. New events append after the current maximum; editing keeps the order unless `storyOrder` is sent. Titles are required, chapter and entity ids are checked against live rows, roles/kinds are bounded, and duplicate links are collapsed. GET joins the chapter number/title and returns links with entity name, type colour and trash state in one pass.

No co-occurrence or inference is used.

Add/edit is one modal with title, chapter, kind, story time, summary and a searchable card picker; the picker infers Person/Place/Item from the card type. Search and kind chips filter the list. ↑/↓ reorders the full list and persists it; Delete asks first. Opening a chapter from an event goes through the existing chapter selection, so dirty-draft protection still applies.
- **No new dependencies.** Reuses the existing `main-inner`, `reader-head`, tabs, modal, field, chip, card and error patterns. Motion is limited to the existing system; the new list rows opt into the same `content-visibility` long-list treatment.

## 52) Explicit relationships
- **Scope.** Authored links between cards, added to the entity editor. No graph is inferred from mentions, chapter order or co-occurrence; a relationship exists only when the writer creates it.
- **Data model.** `server/db.mjs` adds `relationships` (`source_id`, `target_id`, free-text `label`, optional `notes`, timestamps), with `ON DELETE CASCADE` on both card ends and a unique `(source, target, label)` pair. Indexes cover both ends. The label is deliberately not an enum: suggestions include `parent of`, `ally of`, `member of`, `wields` and `owes`, but the writer can type anything.
- **Routes.** `GET /api/entities/:id/relationships` returns every edge touching the card with both names, type icons and trash state. `POST /api/relationships`, `PUT /api/relationships/:id` and `DELETE /api/relationships/:id` create, edit and remove one edge. Self-links, blank labels, missing cards and duplicates are rejected (duplicate is `409`); an update changes only the label and note, because changing ends is a delete-and-re-add.
- **UI.** The entity panel has a **Relationships** section in the main column. It shows outgoing edges with `→` and incoming edges with `←`, the other card, the label and any note, plus edit and delete controls. The add row uses the existing searchable card picker, a datalabel input and an optional note; changes save immediately rather than through the panel's Save button. Opening the other card from a row uses the existing entity navigation.
- **Merge integrity.** Absorbing a card now repoints its relationships onto the survivor. An edge that would become a self-link is dropped, and an edge that would duplicate an existing survivor edge is dropped rather than violating the unique key. The same pass repoints timeline event links, dropping an absorbed `(event, role)` duplicate first; previously a merged card's event link could keep pointing at Trash.
- **Verification.** `npm test` **181/181** (new route test covers directional readback, duplicate/self/blank rejection, label edit, merge repointing and self-link collapse, timeline-link repointing, and cascade deletion); `npx tsc --noEmit` **0**; `npm run build` OK.
